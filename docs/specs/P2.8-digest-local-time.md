# P2.8 Spec: Send the daily digest at 8 am local time

Status: draft, for review. Grounded in `client/src/app/api/digest/route.ts`, `client/vercel.json`, `client/prisma/schema.prisma`, `client/src/lib/tag-queue.ts`.

## 1. Problem

The digest goes out once a day from a Vercel cron at `0 8 * * *` (08:00 UTC) to every user, with the subject "Good morning". For a user in India that is 1:30 pm; in California it is midnight. The greeting is wrong for most people, and the email lands at a random point in their day.

Goal: each user gets one digest per local day, at about 8 am in their own time zone, and the system keeps working when they travel, when clocks change for daylight saving, and when a run crashes halfway.

## 2. How it works today (facts from the code)

- `GET /api/digest`, called by Vercel Cron with `Authorization: Bearer CRON_SECRET`.
- Loads **every** user from Supabase Auth with `admin.listUsers`, 1000 per page, into memory.
- For each user, in one loop inside one function run: skip if no email or `user_metadata.digest_opt_out`, count bookmarks, pick up to 5, send through Resend one email at a time.
- Idempotency key: `digest-<userId>-<UTC date>`.
- There is no `User` table in Postgres; Prisma has `Bookmark`, `Tag`, `Collection`, `CollectionBookmark` only.

What breaks at scale: one function run sends every email in sequence. Vercel stops a function after its time limit, and Resend limits requests per second, so past a few thousand users the run dies partway through and the rest get nothing that day.

## 3. Options considered

**A. Book each user's next send in advance.** After a send, queue a delayed message for that user's next 8 am.
- For: no repeated checking.
- Against: it is a chain. One failed send means the next one is never booked, and the user silently stops getting digests. A time zone change means finding and cancelling the booked message. 10,000 users means 10,000 pending messages to keep in sync.

**B. Check every hour, send to whoever is due.** (Chosen.)
- For: fixes itself. A failed send is retried by the next run; a time zone change needs no cleanup because the next run reads the new value.
- Against: 24 runs a day. With an index (section 4) each run is one lookup whose cost depends on how many users are due, not on how many exist, so this is cheap.

## 4. Data model

A new table, because user records live in Supabase Auth and `user_metadata` cannot be indexed or queried.

```prisma
model DigestSchedule {
  userId       String    @id            // Supabase auth user id
  timeZone     String                   // IANA name, e.g. "Asia/Kolkata"; never a fixed offset
  nextDigestAt DateTime                 // UTC moment of this user's next local 8 am
  lastSentAt   DateTime?

  @@index([nextDigestAt])
}
```

Why the zone name and not an offset: names carry the daylight saving rules ("America/New_York" is UTC-5 in winter, UTC-4 in summer). A stored offset is wrong for half the year.

## 5. Capturing the time zone

Rule: store only what the user's own browser reports. Never guess a zone (from save times, IP or anything else).

- In the browser: `Intl.DateTimeFormat().resolvedOptions().timeZone`, the IANA **name**. Never a local timestamp or an offset: "UTC-5" is New York in winter but also Bogotá all year, which has no daylight saving, so an offset cannot say when clocks change.
- Every save carries it, because every save runs in the user's browser: the website's save form, the extension popup, and the bookmarklet each add a `timeZone` field to `POST /api/bookmarks`. Users who save but never open the app still report their zone.
- The app also reports it on load (`POST /api/account/timezone`), for users who only read.
- Server validates it is a real IANA zone (reject anything `Intl` cannot use, never fail the save over a bad zone), then upserts `DigestSchedule`. If the zone changed, recompute `nextDigestAt`.
- Users whose zone is not known yet: keep 08:00 UTC, exactly as today, until their first save or visit reports a real one. This is the existing behaviour, not a guess.
- Old extension versions that do not send the field keep working; the field is optional.

## 6. The core function (written by hand, not generated)

```ts
// The UTC moment of the first 8:00 local time in `timeZone` strictly after `after`.
function nextLocalEight(timeZone: string, after: Date): Date
```

This is small, but it is where daylight saving bugs live. Test cases, written before the function:

| Zone | After (UTC) | Expect (UTC) | Why |
| --- | --- | --- | --- |
| Asia/Kolkata | 2026-11-06 01:00 | 2026-11-06 02:30 | half-hour offset, same day |
| Asia/Kolkata | 2026-11-06 03:00 | 2026-11-07 02:30 | already past 8 am, next day |
| America/New_York | 2026-11-01 05:00 | 2026-11-01 13:00 | the morning clocks fall back (UTC-5) |
| America/New_York | 2026-03-08 06:00 | 2026-03-08 12:00 | the morning clocks spring forward (UTC-4) |
| Pacific/Kiritimati | 2026-11-06 00:00 | 2026-11-06 18:00 | UTC+14: that 8 am is on 7 Nov locally, still 6 Nov in UTC |
| UTC | 2026-11-06 08:00 | 2026-11-07 08:00 | exactly 8 am counts as past |

Open question: whether to use `Temporal` or `Intl`. `Temporal` makes this easy but may not be available in every runtime Ritro uses (Vercel Node version, Vitest). Check before writing; fall back to `Intl.DateTimeFormat` with `formatToParts`.

## 7. The job

1. **Cron, hourly** (`0 * * * *`), hits `GET /api/digest` (same `CRON_SECRET` check).
2. **Find who is due**: `SELECT userId FROM DigestSchedule WHERE nextDigestAt <= now() ORDER BY nextDigestAt LIMIT 500`. Loop pages until empty or close to the time limit.
3. **Queue, do not send**: for each batch, publish to QStash with the existing `Client().publishJSON` pattern (`lib/tag-queue.ts`), pointing at a new worker `POST /api/jobs/send-digest` protected by `verifySignatureAppRouter`, like `jobs/tag-bookmark`.
4. **Worker sends**: skip opted-out users and users with no bookmarks, pick up to 5 bookmarks, send with Resend (batch API where it fits), using an idempotency key built from the user's **local** date: `digest-<userId>-<local YYYY-MM-DD>`.
   Greeting: "Good morning" in the subject only when the user's zone is known (the send is then always at their 8 am). Zone still UTC: the neutral subject, plus one line in the body: "Open Ritro once and we'll send this at 8 am your time."
5. **Only after a successful send**: set `lastSentAt = now()` and `nextDigestAt = nextLocalEight(timeZone, now())`. Users skipped for opt-out or no bookmarks also move to their next 8 am, so they are not re-checked every hour.

Rule this design follows: mark progress only after the work succeeds, and make the work safe to repeat.

## 8. Failure and edge cases

- **Crash halfway through queueing**: users not yet queued still have `nextDigestAt <= now()` and are picked up next run. Users queued twice send with the same idempotency key, and Resend drops the repeat within 24 hours.
- **Send fails**: `nextDigestAt` does not move, the next hourly run picks the user up again, QStash also retries the worker.
- **Travel or moving**: the app reports a new zone, `nextDigestAt` is recomputed. Guard against two digests in one real day (fly east to west after getting one): skip if `lastSentAt` is within the last 20 hours.
- **Daylight saving**: handled by storing the zone name and computing each next 8 am from it, one day at a time.
- **Half-hour and 45-minute zones**: an hourly cron finds them up to 59 minutes after 8 am (8:30 for India). Acceptable; a 15-minute cron would tighten it if needed.
- **Busy hours**: 8 am in India or the US East Coast covers far more users than mid-Pacific. The queue absorbs the spike.
- **Opt-out**: still read from `user_metadata.digest_opt_out` in the worker; no change.

## 9. Rollout

1. Migration: create `DigestSchedule`. Live production database: additive only, no existing table changes.
2. Backfill script: one row per existing user with bookmarks, `timeZone = "UTC"`, `nextDigestAt = next 08:00 UTC`. Users see no change until their browser reports their real zone.
3. Ship zone capture first (save requests from site, extension and bookmarklet, plus app load) and let real zones fill in for a few days. The extension needs a new release for its saves to carry the zone.
4. Switch the cron from daily to hourly and the route from "send everyone" to "queue who is due" in the same deploy.
5. Check: the plan supports an hourly Vercel cron. If not, run the hourly trigger from a QStash schedule instead.

## 10. Tests

- `nextLocalEight`: the table in section 6.
- Due query: only rows with `nextDigestAt <= now()` are returned, in order, limited.
- Worker: advances `nextDigestAt` on success, leaves it on a Resend error, skips opt-outs and moves them forward, uses the local-date idempotency key.
- Time zone endpoint: rejects an invalid zone, recomputes on change, rejects unauthenticated calls.
- `POST /api/bookmarks`: a valid `timeZone` updates the schedule; a missing or invalid one still saves the bookmark.

## 11. Out of scope

- Letting users pick their own send time or pin a home time zone. Readwise offers a send-time setting for its Daily Review email; Ritro can add it later with a `digestHour` column (default 8) and `nextLocalHour(tz, hour, after)`. The hourly job would not change.
- Redesigning the digest email body (it still uses the old colours and "Hey 👋").
- Open or click tracking (P3.7).

## 12. Decisions

- Precision: hourly cron. (Owner, 2026-11-06.)
- Unknown zone: no guessing. The zone comes only from the user's browser, sent with every save and on app load; until then 08:00 UTC as today. (Owner, 2026-11-06.)
